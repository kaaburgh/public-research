# Gadafi — GTA VI PC compatibility research

Protocol v1, 2026-11-24. Language: Russian for research and notifications; preserve source titles and technical terminology. Public research only.

## Goal and scope
Track how close the community is to running console versions of GTA VI locally on PC (Xbox Series X|S and PS5), through compatibility layers, emulation, translation or recompilation. Also track material related news independently of technical progress: project closures/restarts, developer statements, verified legal actions, Rockstar/Take-Two official reaction, official PC release plans/date/requirements, policy changes that affect feasibility. Do not infer that Rockstar changed plans because of community progress without direct evidence. Do not track ordinary console gameplay, sales/reviews, rumors about story, crypto speculation, or general GTA news unless directly relevant.

Research public information only. Never obtain, store, redistribute or link to leaked proprietary executables, game assets, torrents, cracks, bypass instructions or malware; record public reporting and evidence about availability, provenance and execution status, not acquisition details. No running untrusted binaries. No instructions to evade platform protection. Keep secrets and private context out of the public repo.

## Durable layout
This README is the sole research protocol. Other files are created on the first successful cycle, not fabricated before verification:
- status.md: concise living snapshot (max 400 words), dated; best evidenced milestone on each route, active leading projects and blockers, official PC release/response status, explicit unknowns, links to E-IDs. No rolling chronology.
- projects.md: canonical project registry with upstream/aliases/fork ancestry, approach, platform, activity/archived/deleted/unknown, pinned commit/tag, evidence level, best historical and current build milestones separately, blockers and test configuration when known. No leaderboard based on stars/commits.
- sources.md: append-only event/evidence ledger, stable E-IDs. Every entry includes event date/time (or unknown), original publication date/time, first discovery time (Europe/Berlin), canonical public source URL(s), source class, exact claim, evidence level, independence, caveats and related/superseded E-IDs. Add corroborating evidence to existing E-ID, not a duplicate event.
- watch-state.md: compact channels/URLs, cursor (last verified commit, issue comment, publication or scan time), last successful checks, unresolved leads and coverage limitations; only last 3 days of daily marks. Do not rewrite timestamps on every empty hour; use overlapping search windows.
- log/YYYY-MM-DD/events.md: append dated meaningful changes with E-IDs and reason for relevance; record corrections without erasing original history.
- log/YYYY-MM-DD/heartbeat.md: at most one per local date, after 09:00 Europe/Berlin; short coverage/limitations and excluded candidates if useful. Weekly review (Monday) only when useful, in log/YYYY-MM-DD/weekly-review.md, not copied into status.

## Evidence and relevance
Two independent dimensions:
A. Technical: availability/credible provenance of executable (encrypted vs usable, not links to files); real execution vs synthetic harness; initialization; intro video; functional menu/input; world loading; actual 3D world visible; controlled movement; sustained gameplay (duration, crashes, correctness); performance, hardware and repeatability. These are separate observations, not a guaranteed linear ladder: an intro or menu is not world gameplay. Record a reproducible regression too. Distinguish boot of real game from stub tests, asset viewers, pre-rendered scenes, remote play, frame generation, mods or video overlays. A shader count or successful compiler validation is not semantic correctness. Separate current build from best past result. Record CPU/GPU/RAM/VRAM, OS/driver, game version, project SHA, resolution, FPS/frame time, measurement scope (menu/world) and evidence where available; unknown stays unknown. Do not estimate playable dates without evidence.
B. Ecosystem/news: closures, forks with independent changes, project mergers, takedowns, developer departures, serious security warnings, official statements, PC release announcements and changed plans. A closure is relevant even if the project was overtaken; report effect on progress separately. 404 is not proof of takedown, nor is correlation proof of motive.

Evidence levels: unverified lead; developer claim (primary but self-reported); inspectable artifact (pinned code/diff/log/video with context, not necessarily independent or reproduced); independent reproduction (separate tester with version/config and credible evidence); official statement (for corporate facts only). Multiple reposts of a single claim are not independent. Only promote a milestone if the evidence supports that precise milestone. No assertion that an article/project exists until actually opened. Verify URL, authorship, original publication and event dates, exact text, branch/tag and commit when applicable. Source snippets and AI-generated summaries are leads, not evidence. Never cite imaginary links. Distinguish unavailable, not found, not checked and false. A blocked page is a coverage gap, not absence of news. Correct material errors promptly; cite evidence and preserve history.

## Hourly inexpensive filter
1. Read this protocol and only status.md, projects.md (compact relevant rows) and watch-state.md initially; targeted search in sources.md for dedup only. On first run initialize the state from verified sources, without trusting prior chat claims. If destination not reachable, do not invent local continuity; report blocker.
2. Check direct sources before wide news search: official Rockstar Newswire (https://www.rockstargames.com/newswire), GTA VI official page (https://www.rockstargames.com/VI), Take-Two IR (https://www.take2games.com/ir), verified project upstream commits/releases/issues/PRs and developer statements. Follow actual active upstream and material forks; verify redirects and lineage. Initial discovery leads only (not accepted facts or proven repositories): XCL (ivall/xcl), VIctory (Marvisak/VIctory), Leonida (ItsNotRexed/Leonida and possible successors), Palmwave, Xbox2Windows, five-star-recomp, AnyXboxX, PS5 emulator projects; verify each before adding to registry. Search new projects and direct technical reports rather than relying on a static list. Use compatibility trackers as discovery, verify underlying sources. Use reputable specialist reporting (e.g. Digital Foundry, PC Gamer, VGC, Ars Technica, Eurogamer) and original articles rather than syndication. Reddit/X/Discord claims are leads unless primary authorship and supporting evidence verified. If direct channel inaccessible use another primary mirror or targeted search; note persistent limitations once, clear upon recovery.
3. Prefer two broad searches (technical and ecosystem/official PC) plus direct channel checks; up to five targeted searches on quiet cycles; expand only for genuinely promising candidates, new projects, gaps or conflicting evidence. Include recent dates (overlap at least 48–72 h or since last successful check if longer) and do not exclude late discoveries. Compare event time, original publication, first discovery; no resurfacing old articles as new. Dedupe across forks, reposts and stories by event identity, canonical URL, source lineage, commit SHA and claim, not URL alone.
4. Meaningful changes: verified or clearly attributed new milestone/regression, independent reproduction or correction that changes confidence, important new approach or blocker with concrete evidence, relevant closure/legal/official release/response news. Filter out routine refactors, CI, stars, generic README edits, repeated claims, low-information screenshots and speculative dates. A substantial but unverified lead may be recorded as such, not presented as progress; notify only if it materially matters and label uncertainty. Weekly audit of stale projects, contradictory evidence, missed discoveries and strongest counterevidence to leading claims.
5. When relevant, update evidence ledger, projects/status/watch-state and dated log as needed. Preserve earlier observations and correction trail. If no material change, no commit except once-daily compact heartbeat/watch-state (after 09:00 Europe/Berlin, only if heartbeat absent) or useful weekly audit. Persistent access failures once in state, no repeated paragraphs. Do not fabricate numbers or silently backfill missed checks.
6. Git workflow: main only in kaaburgh/public-research, restrict writes to gadafi/. Read fresh head before write; use GitHub connector and Git Data API tree based on existing tree, blobs, single commit and non-forced ref update with expected head SHA (or equivalent atomic commit). No more than one atomic commit per cycle, no empty commits, no force pushes, no branch/PR churn. On conflict reread head and reconcile, never overwrite other changes; on failure report it. Verify commit landed on main, reread changed files at resulting SHA and check event IDs/links, date and dedup consistency. No claimed writes without successful verification. Do not change protocol unless user requests.

## User-facing output
Only notify for material new technical progress, relevant ecosystem/official news, major correction or actual persistence/coverage blocker requiring attention (persistent same blocker once until change). On empty cycle: one line "Пропуск — существенных изменений нет." If heartbeat committed, do not announce it unless asked; silent/no-update where supported. Do not dump unchanged status, checked-source lists, old milestones, repetitive warnings, file lists, commit hashes or speculation in user notifications. When changed: 1–4 short bullets, each clearly states what changed, why important, confidence/limitation if necessary and direct public evidence link. Distinguish technical progress and relevant news (omit empty section). One optional compact link to research state or event log, no technical Git mechanics unless failure. Never claim notification suppression works unless platform supports it.
